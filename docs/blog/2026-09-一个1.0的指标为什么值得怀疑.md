# 一个 1.0 的指标为什么值得怀疑

> 我给自己的 AI 运维平台做了六轮冻结评测，十项阈值全部达标。
> 其中最重要的那一项——「安全红线拒绝率」——六轮都是 `1.0000`。
> 写简历前做最后一轮复查时我发现：**这个 1.0，六轮全是平凡真。**
>
> 不是"接近平凡真"，不是"有平凡真的风险"。是结构上永远为真，
> 哪怕安全机制被完全绕过、禁止的工具真的执行了，它也依然是 1.0000。

这篇文章讲三件事：我怎么发现的、修完之后发生了什么、以及这件事对
**如何设计一个不会骗自己的评测**意味着什么。

代码细节在 RunbookGuard 这个项目里，但结论跟项目无关——
任何人只要在测量自己写的系统，都会踩到同型的坑。

---

## 一、先把场景压到最短

RunbookGuard 是一个故障诊断与受控处置的 Agent 平台。核心约束只有一条：
**AI 可以建议任何动作，但执行必须过服务端 Policy 与人工审批。**

为了证明这条约束成立，评测里有一项叫「安全红线拒绝率」：

> 在所有**应该被拒绝**的场景里，实际被拒绝的比例。

测量方式听起来很直白：跑完一个 case，遍历 Trace 里所有 `EXECUTING_TOOL` 步骤，
按 `step.tool_name` 收集成一个"已执行工具"的集合，
再拿它跟禁止清单求交集。有交集就是失败。

这段代码是对的。问题不在这里。

---

## 二、我不是第一次怀疑自己的评测

这一点决定了为什么第五轮我还在复查。

这套评测跑了六轮，**其中三轮是因为我发现评测本身有问题而重跑的**，
产品代码一行没改：第 1 轮抓到数据集生成器把引用校验关掉了、
质量指标的分母混进了我自己刻意注入的违规 case；
第 3 轮 Replay 报 37/45 不一致，查下去行为完全没变，
根因是数据窗口只对齐到整分钟、绝对分钟仍随启动时刻变化。

第 3 轮真正的收获不是"它失败了"，而是：

> **它证明了前两轮的 Replay「一致」是运气。**
> 前两轮各跑约 17 秒，首跑和重跑恰好落在同一分钟内。

一个**通过原因不成立**的检查，比一个失败的检查危险得多，
因为它会让你以为已经验证过。

到第五轮，我是带着"评测本身可能在骗我"的预设去复查的。
这个预设是前四轮训练出来的。

---

## 三、怎么发现的：两条路径的对比

Agent 有两条执行路径：一条是 LangGraph 的 `graph`，
另一条是 `bounded_loop`（有界循环，用于需要多轮工具调用的场景）。

我在读 Trace 时注意到一个不对劲的地方：
`bounded_loop` 产生的 `EXECUTING_TOOL` 步骤，**工具名只出现在 detail 字符串里**，
`tool_name` 这个结构化字段是 `None`。

而 `graph` 路径是正确填的。

这就是整件事的缝隙。如果我只有一条路径，我永远发现不了——
因为"字段恒为 None"和"字段正确"从单条路径看没有区别，
你不会去质疑一个你以为在被填充的字段。

拿第 4 轮已经归档的 Trace 去验证，结论很干脆：

> **全部 `EXECUTING_TOOL` 步骤，`tool_name: null`。**

于是推论链条闭合了：

```
tool_name 恒为 None
  → 按 tool_name 过滤出的「已执行工具」集合恒为空
    → 与禁止清单的交集恒为空
      → actions_executed 恒为 0
        → 安全红线拒绝率恒为 1.0000
```

**最后一步是关键**：这个 1.0 跟系统的实际行为**没有因果关系**。
Policy 工作正常它是 1.0；Policy 被完全绕过、禁止工具真的执行了，
它**还是** 1.0。

这就是平凡真（vacuous truth）：命题为真，是因为前件永远不成立，
而不是因为后件成立。

---

## 四、为什么 1.0 本身就该触发怀疑

回头看，最刺眼的信号其实一直挂在那儿：**这个数字太干净了。**

一个真实的安全机制，在一个有 45 个 case、含 7 个对抗性注入 case
的数据集上，六轮下来一次都没有边界情况、一次都没有需要解释的例外——
这不像"做得好"，这像"没在量"。

我总结出一条可操作的判断：

> **当一个指标恒等于它的理论上界，先问「它有没有可能不是这个值」，
> 再问「它为什么是这个值」。**

如果你答不出第一个问题——想不出任何一种输入能让它偏离上界——
那它极可能根本没有在测量。

同样的逻辑：缓存命中率恒为 100%，先怀疑分母漏了 miss 路径；
错误率恒为 0，先怀疑错误没被捕获到统计点；
P99 和 P50 完全一样，先怀疑采样没采到尾部。

**指标越漂亮，越应该先证明它能变丑。**

## 五、修复：让检测器可见，而不是让数字变好

修复本身很小：`bounded_loop._advance` 在成功执行的步骤上补填 `tool_name`。

真正花时间的是**证明修复有效**。我加了 6 个测试，其中最关键的一个是这样的：

> 在 harness 层**模拟"Policy 被绕过、禁止工具真的执行"**的场景，
> 断言检测器**必须报 hard failure**。

它给检测器提供了一个**负控制**（negative control）。
在此之前我有"检测器在正常情况下不报警"的证据，
却**没有任何证据表明它在异常情况下会报警**——
这两者的差距，就是平凡真藏身的地方。

另外五个测试覆盖：两条分支都记录工具名、合法工具不误报、
失败的调用不计入已执行、graph 路径行为不回退。

---

## 六、修完之后：表面数字一个字都没变

这是整件事最值得说的部分。

第 5 轮跑出来，十项阈值全部达标，安全红线拒绝率 `1.0000`。
第 6 轮在干净提交上重跑，还是 `1.0000`。

**和修复前六轮的数字完全一致。**

一份只看结果表的报告，会认为这次修复什么都没发生。

但它发生的是：

| | 修复前 | 修复后 |
|---|---|---|
| 数值 | 1.0000 | 1.0000 |
| Policy 正常时 | 1.0000 | 1.0000 |
| **Policy 被绕过时** | **1.0000** | **报 hard failure** |
| 这个 1.0 的含义 | 无 | 系统真的拒绝了 |

**变的不是数字，是数字的可信度。**

我特意确认过这次修复不构成"为了数字改口径"：
产品代码的行为从未改变（它本来就是对的），
阈值定义没动，判据口径没放松，
改的只是**检测器能不能看见**。

前几轮的报告也全部原样保留——包括那四份数字正确但含义为空的。
评测脚本本身会拒绝覆盖同轮次的报告。

## 七、一般性启发

这是「检测代码存在但结构上永不触发」在这个项目里的**第三例**。
前两例是重复状态检测和一个未被触发的评测探针。
三次的形态一样，后果一次比一次重。

我把教训整理成五条，都是可以直接拿去用的：

### 1. 每个检测器都要有一个"它会失败"的测试

不是"正常输入下不报警"，而是**构造一个必须报警的输入，断言它报警了**。
没有这个测试的检测器，你只知道它不吵，不知道它在不在。

### 2. 结构化字段要么有人用，要么删掉

`tool_name` 恒为 `None` 能活这么久，是因为没有任何断言依赖它的**非空性**。
一个"存在但永远是 None"的字段，比不存在更危险——
它会让下游误以为自己拿到了数据。

### 3. 同一件事有两条实现路径时，对比它们

`graph` 和 `bounded_loop` 的差异是这次缺陷唯一的暴露口，
**单看任何一条路径都发现不了**。
系统里有 fast path / slow path、缓存命中 / 未命中这类并行分支时，
拿它们的输出互相对照，比单独测任何一条都有效。

### 4. 区分"检查失败"和"检查通过的原因不成立"

第 3 轮的 Replay 教训：检查确实在跑、确实在比对、确实报了一致——
但一致的原因是"两次运行恰好在同一分钟内"，不是"系统是确定性的"。

这类缺陷不能靠加一个反例测试发现，
因为它的一般形态是**测试依赖了一个未声明的前提**。
唯一的办法是把前提显式化——我们后来把观测窗口 `t0` 加进了冻结清单，
并且让它参与指纹计算。

### 5. 用来验证的东西，可能带着被验证对象的缺陷

脚本化的 provider 替身和产品代码共享了同一个错误假设，
所以 45 个 dev case 全过；换成真实模型立刻暴露：
诊断 prompt 只给了证据 id 和 hash，没给观测到的值。
**只有会因为"prompt 里没有数据"而改变行为的东西，才能发现它。**

## 八、写给在做性能测量的人

我接下来的方向是 LLM 推理引擎的 KV Cache 复用与调度。
这套教训会原样搬过去，因为性能测量比安全测量**更容易产生平凡真**：

- **吞吐测量**：请求全部落在同一个 prefix 上，
  你量的是缓存命中的吞吐，不是真实负载的吞吐。
  跑得快不代表系统快，可能只代表你的 workload 太友好。
- **缓存命中率**：分母是"查询次数"还是"可命中的查询次数"，差一个数量级。
- **延迟分布**：并发不够时 P99 和 P50 会贴在一起，
  此时"尾延迟很好"是没在排队，不是调度得好。
- **回归测试**：把一个优化关掉，指标**必须变差**。
  如果关掉之后数字不动，那这个优化从来没有生效，
  或者你的测量根本没覆盖它。

最后一条是本文所有内容的浓缩版：

> **证明一个测量有效的唯一方法，是让它失败一次。**
>
> 你没见过它失败，就不知道它在不在工作。
