# M0 — 不做清单（Non-Goals）

- 里程碑：M0
- 状态：Draft，待 Gate 验收
- 上游依据：说明书 §8 / §11 / §25，DEV_PROMPT §4 / §14

本清单是**硬性约束**，不是"暂时没空做"的待办。每条包含一句话定义、`理由`、以及 `重新评估条件`（即什么情况下才允许重新讨论）。M0 Gate 要求每条都有理由——所以清单里不允许出现"因为不需要"这种无信息量的理由。

未列在本清单、但也不属于当前里程碑交付物的功能，默认同样不做（默认拒绝原则同时适用于产品行为与开发范围）。

---

## A 产品行为禁止（说明书 §8）

### NG-1 任意 shell 执行

不提供任何能执行模型生成的 shell 命令 / 脚本 / 代码的工具。

**理由**：一旦存在通用 shell，全部权限设计立即失效——Policy 无法对 `bash -c "$arg"` 做有意义的判定，allowlist、tenant binding、参数摘要审批全部被绕过。工具集必须是**有限枚举**的，这样 Policy 才可能是纯函数且可单测。

**重新评估条件**：永不。即使未来需要扩展能力，也只能新增有明确 schema 的具名工具。

### NG-2 真实生产 Kubernetes 写入

不对任何真实集群做写操作。所有处置只作用于 `services/synthetic-lab/`。

**理由**：项目自身的能力边界尚未被评测证明（M6 前所有阈值都是"未验证"）。在未证明安全性之前接触生产，风险与收益完全不对等。同时公开仓库如果内置生产写入路径，任何使用者的误配置都会变成真实事故。

**重新评估条件**：M6 五项阈值全部达标 + 有真实用户在其自有环境显式配置并承担风险 + 提供独立的 dry-run 与两人审批模式。属于 v1.x 议题。

### NG-3 自动删除 Pod / Volume / 数据库 / 远端资源

不提供任何删除类工具，即使目标在 synthetic-lab 内。

**理由**：删除是不可逆动作，与"审批后可撤销"的安全模型不兼容；而且它对诊断能力的证明没有增量价值——重启 / 回滚 / 限流已足够覆盖处置语义。

**重新评估条件**：永不（第一版）。若未来需要，必须先有资源快照与回滚机制。

### NG-4 任意公网访问

Agent Runtime 与工具执行进程默认禁止出网；只允许 egress allowlist 内的地址（模型 Provider、本地中间件）。

**理由**：出网能力叠加"不可信输入"（日志、Runbook）等于把 Prompt Injection 直接升级为数据外泄通道。同时它让评测不可复现——外部网络是不受控变量。

**重新评估条件**：需要新增外部数据源时，逐个加入 allowlist 并在 ADR 记录，不放开默认策略。

### NG-5 Secret 进入 Prompt / Trace / 日志 / Artifact / 评测报告

不允许任何凭据出现在这五处。

**理由**：Trace 和评测报告是要公开或长期留存的；Prompt 会被记录与 replay。一次泄漏是永久泄漏。这条同时是威胁模型 T-3 的对应约束。

**重新评估条件**：永不。脱敏是无条件要求。

### NG-6 无上限 Agent 循环

任何 Run 都必须同时受 max_steps、wall-clock deadline、token/cost budget、tool-call budget 约束，且有 repeated-state 检测。

**理由**：没有硬上限的 Agent 在故障场景下会稳定地烧钱并制造噪声，而且无法评测（一个可能永不终止的系统没有"成功率"这个指标）。八条终止条件每条都要有单测。

**重新评估条件**：永不。上限值可调，上限本身不可移除。

### NG-7 复杂多 Agent 编排

单 Agent + 有界状态机。不做 planner/executor 分裂、不做 agent 间自由对话、不做动态生成子 Agent。

**理由**：多 Agent 会让状态空间和失败模式爆炸，直接冲击本项目的三根支柱——恢复语义（谁的 Checkpoint？）、评测归因（哪个 Agent 错了？）、审批边界（谁的建议？）。收益是 Demo 观感，代价是可验证性。

**重新评估条件**：M6 通过、单 Agent 成功率稳定在阈值以上，且能明确指出某类 case 单 Agent 结构上无法解决。

### NG-8 用一个成功截图 / 录像声称生产可用

不用 Demo 替代评测结论。

**理由**：一次成功不构成能力证明，而"看起来能用"是这类项目最常见的失真来源。能力主张只能来自冻结配置下的正式评测，且演示必须准备**失败版本**（说明书 §28）。

**重新评估条件**：永不。

### NG-9 自研大模型 / 训练框架 / CUDA 算子

不训练、不微调、不写 kernel。

**理由**：这与项目要证明的能力（Agent 安全、可评测、可恢复）没有交集，只会稀释工程量。模型层通过 OpenAI-compatible Adapter 保持可替换。

**重新评估条件**：有真实 JD 要求且有 GPU 资源时，作为**独立项目**开展，不并入本仓库。

## B 技术栈排除（说明书 §11、DEV_PROMPT §4）

### NG-10 第一版不引入 Kafka

消息层只用 RabbitMQ。

**理由**：本项目要证明的是 Lease / Heartbeat / 幂等 / 死信 / 唯一终态这些**语义**，RabbitMQ 已完全覆盖，且与既有 FrameFlow 经验形成迁移。引入 Kafka 只增加运维复杂度和 Compose 启动成本，不增加任何可验证结论。

**重新评估条件**：出现真实吞吐瓶颈且已用数据证明 RabbitMQ 是瓶颈。M8 之前不讨论。

### NG-11 第一版不引入 Elasticsearch / Milvus / Temporal / Spring Cloud / 第二个 Agent 框架

检索用 Qdrant + 关键词基线；编排用 LangGraph；Java 侧单体 Spring Boot。

**理由**：每多一个中间件，本地一键复现（M7 Gate）的失败概率就上升，而它们解决的都是当前规模不存在的问题。Temporal 尤其危险——它会替代掉本项目要亲手实现的 Lease / Checkpoint 语义，等于把核心考点外包出去。第二个 Agent 框架同理。

**重新评估条件**：单个组件出现被数据证明的能力缺口，且在 ADR 中说明为什么现有栈不能解决。

### NG-12 不使用 JPA / Hibernate

Java 侧持久层固定 MyBatis。

**理由**：本项目需要显式控制 SQL、乐观锁（Incident.version）、幂等 upsert 与审计追加写，这些在 MyBatis 下是可读可审的；ORM 的自动行为会掩盖并发与索引问题，而这恰好是要能解释清楚的部分（说明书 §27）。

**重新评估条件**：不重新评估。

### NG-13 不使用云资源

集群只用本地 kind 或 k3d；不申请托管数据库、托管 MQ、云 K8s。

**理由**：评审者必须能在自己机器上完整复现。依赖云资源会让"可复现"变成"需要我的账号"。

**重新评估条件**：永不（对本项目的公开版本而言）。

## C 过程纪律禁止（说明书 §25、DEV_PROMPT §14）

### NG-14 一次生成整个项目 / 同时开发多个里程碑

一次只做一个里程碑，Gate 未通过不进入下一个。

**理由**：这类项目的失败模式不是写不完，而是写了一堆互相矛盾且没测过的代码。分里程碑 + Gate 是唯一能保证每层都被真实验证的机制。也是本项目对外可讲的工程纪律本身。

**重新评估条件**：永不。

### NG-15 用 README 代替源码 / 用 mock 冒充真实 Provider / 用本地通过冒充公开证明 / 未过 Gate 就写进简历

不许把没做的事写成做了。未实际运行验证的结论必须标 `UNKNOWN` 或 `未验证`。

**理由**：这是项目定义里的第一红线。一旦文档与代码脱节，整个仓库的可信度归零，而这个项目的全部价值建立在"可以被当场质疑并验证"上。CI 默认使用 fake provider 是**为了确定性**，因此必须在文档中显式标注哪些结论来自 fake provider、哪些来自真实模型。

**重新评估条件**：永不。

### NG-16 为了简历数字修改评测口径 / 反复运行到 PASS / 开发期查看 incidents-held

`incidents-dev` 用于开发调试；`incidents-held` 只在正式评测时使用，开发期不看不调。正式评测前冻结 commit / dataset / prompt / model / tool 版本 / evaluator / 阈值。

**理由**：held set 一旦被看过就永久失效，无法恢复。反复运行到 PASS 等于用随机性挑选结果，得到的数字没有意义。阈值是**预声明**的，事后调整口径就是自欺。

**重新评估条件**：永不。若阈值确实不现实，正确做法是**停下来说明**并重新预声明一轮，而不是悄悄改口径。

### NG-17 第一版不做的产品功能（范围外功能明细）

以下功能不在 M0-M8 范围内，即使实现成本低也不做：

- 营销页 / Landing page / 文档站（控制台只做 Incident 列表、Run 详情与时间线、证据与引用、审批操作、Trace 查看）。
- Runbook 在线编辑 UI（Runbook 以文件形式版本化，通过 ingest 流程进入索引）。
- 用户自助注册、密码找回、邮件通知、Webhook / Slack 集成。
- 多区域部署、计费中心、SaaS 化、租户自助开通。
- 告警接入适配器（PagerDuty / OpsGenie / AlertManager 等），第一版告警来源只有 synthetic-lab。
- 真实可观测栈适配器（Prometheus / Loki / 真实 K8s 只读接入），属于 v1.x。
- 移动端、暗色主题定制、i18n。
- 管理层报表 / 自定义仪表盘导出。

**理由**：这些都属于"让产品看起来完整"，但对三根支柱（安全 / 可评测 / 可恢复）零贡献。它们的共同特征是工程量可观且无法用测试证明价值。第一版的完整性由**演示脚本能否跑通**定义，不由功能数量定义。

**重新评估条件**：有真实用户明确要求，且该功能不削弱现有安全边界。

## D 判据

遇到任何"要不要顺便加一下"的念头，按下面顺序自问：

1. 它让安全 / 可评测 / 可恢复中的哪一项更强？说不出来 → 不做。
2. 它能不能被一个会失败的测试证明？不能 → 不做。
3. 它是否属于当前里程碑交付物？不属于 → 记录到本清单或 backlog，不做。

## E 未验证项

- 本清单是否完整覆盖了所有会导致范围蔓延的方向：`未验证`。清单会随里程碑推进增补，增补需在此文件留痕，不允许静默放宽。
