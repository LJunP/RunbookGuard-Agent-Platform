# ADR-0002：`arguments_digest` 的规范化与摘要算法

- Status: Accepted
- Date: 2026-08-26
- 里程碑：M1（M0 Gate 报告 §5.1 B3 的阻塞项）
- 关联：[威胁模型 T-2](../architecture/M0-threat-model.md)、[ADR-0001](ADR-0001-scope-freeze-and-spec-conflicts.md)

## Context

威胁 T-2「审批后篡改参数」的缓解依赖一个前提：**审批时绑定的参数摘要，必须能在执行时被重新计算出完全相同的值**。这要求参数的序列化是**确定性的**——同一组语义参数，无论经过 JSON 反序列化 / 序列化多少轮、无论键的插入顺序如何，都必须得到同一个字节序列。

朴素做法（直接对收到的 JSON 字符串做 SHA-256）在跨语言链路里必然失败：Java Control Plane 收到审批请求时的 JSON 文本，与 Python Agent Runtime 执行时构造的 JSON 文本，几乎不可能逐字节相同（键顺序、空格、数字表示、Unicode 转义都会不同）。结果是**合法请求被误拒**——这是 M0 Gate 报告已经预警的两类缺陷之一。

反方向的缺陷同样致命：如果规范化过于宽松（例如把数字统一转成字符串、或忽略大小写），不同语义的参数可能产生相同摘要，攻击者就能构造一个"摘要相同但语义不同"的参数绕过审批。

## Decision

### 1. 采用 RFC 8785 JSON Canonicalization Scheme (JCS) 的受限子集

规范化规则：

1. **对象键排序**：按键的 UTF-16 码元序列做字典序排序（RFC 8785 §3.2.3 的要求）。
2. **无多余空白**：分隔符只有 `,` 和 `:`，不带空格。
3. **字符串转义最小化**：只转义 JSON 必需的字符（`"`、`\`、以及 U+0000–U+001F 控制字符，其中 `\b \f \n \r \t` 使用两字符短形式，其余用 `\u00XX`）。非 ASCII 字符**不转义**，直接以 UTF-8 输出。
4. **数字序列化**：见第 2 节。
5. **输出编码**：UTF-8。
6. **摘要**：对规范化后的 UTF-8 字节做 SHA-256，输出小写十六进制（64 字符）。
7. **算法标识**：摘要与算法标识一起持久化（`digest_alg = "JCS-SHA256-V1"`），使未来更换算法时旧记录仍可解释。不允许只存摘要不存算法版本。

### 2. 数字：**限制输入域**，而不是实现完整的 ES6 数字序列化

RFC 8785 要求数字按 ECMAScript `Number::toString` 序列化，这在 Java 里正确实现需要处理 Ryū 短表示等细节。本项目不实现它，而是**收窄合法输入域**：

- **整数**：允许，范围限制为 IEEE-754 双精度可精确表示的整数区间 `[-(2^53-1), 2^53-1]`，序列化为最短十进制形式（无前导零、无 `+`、无小数点、无指数）。
- **浮点数**：**拒绝**。工具参数中出现非整数数字时，规范化过程抛出 `NonCanonicalizableArgumentException`，请求被拒绝。
- **理由**：工具参数的实际语义（服务名、版本号、时间窗口秒数、限流百分比、日志条数上限）都能用整数或字符串表达。浮点数在跨语言链路中的表示差异（`0.1`、`1e-1`、`0.10000000000000001`）是纯粹的风险来源，收益为零。宁可让参数设计受限，也不要让摘要可能不一致。
- 若未来确实需要小数（例如限流到 12.5%），正确做法是改用整数基点（`1250` 表示 12.50%）或字符串，**不是**放开浮点。

### 3. 其它明确的拒绝规则（fail-closed）

规范化遇到以下情况一律抛异常拒绝，而不是"尽力处理"：

| 情况 | 原因 |
|---|---|
| 浮点数 / `NaN` / `Infinity` | 见第 2 节 |
| 超出 `[-(2^53-1), 2^53-1]` 的整数 | 双精度不可精确表示，跨语言必然分歧 |
| 嵌套深度 > 8 | 防御性上限，同时避免栈溢出 |
| 键或值的总规范化长度 > 8 KiB | 参数不该这么大；超限说明有人在塞数据 |
| 重复键 | JSON 解析器行为不一致（后者胜 / 前者胜 / 报错），不接受歧义输入 |
| 顶层不是 JSON 对象 | 工具参数契约固定为对象 |
| 字符串含未配对的 UTF-16 代理项 | 无法确定 UTF-8 编码，且是常见的注入/规避手法 |

`null` **允许**，序列化为 `null`。**注意语义陷阱**：`{"a":null}` 与 `{}` 的摘要不同（前者显式传了空值）。这是刻意的——不做"空值等价折叠"，因为折叠会让两个不同的工具调用共享一个摘要。调用方必须保证参数构造方式稳定。

### 4. 摘要覆盖范围：不只是参数

`arguments_digest` 只覆盖参数本身。但审批要绑定的语义是"**谁**批准了对**哪个资源**执行**哪个工具**的**哪组参数**"。因此 Approval 记录中 `tool_name`、`resource_ref`、`tenant_id` 与 `arguments_digest` **共同**构成校验单元，执行前四者全部比对，不是只比对摘要。

**为什么不把它们拼进摘要**：拼进去会让摘要不可解释（无法从 Approval 记录看出批准的是哪个工具），而且会在拼接处引入分隔符注入风险（`tool="a", args={"b":"c"}` 与 `tool="a\u0000b", args={"c":...}` 可能拼出同一串）。分字段存储 + 分字段比对更清晰，也更容易在审计里回溯。

### 5. 单次使用（single-use）

Approval 增加 `consumed_at` 字段。执行成功后标记消费；已消费的 Approval 不能再次放行。

**理由**：仅靠"摘要一致"无法阻止**重放**——同一份批准被用来执行两次同样的动作（例如回滚两次）。这与 T-6「重复副作用」直接相关。消费标记 + 幂等键是两道独立防线：前者防"故意重放已批准的动作"，后者防"消息重投导致的意外重复"。

## Consequences

**正面**：

- 跨语言摘要一致性有明确、可测试的规则，Python 侧只需实现同一份规则（M4 落地，并用共享测试向量交叉校验）。
- fail-closed 设计让所有歧义输入变成显式拒绝，不会静默产生错误摘要。
- `digest_alg` 版本化，未来可迁移。

**负面 / 代价**：

- 工具参数**不能使用浮点数**。这是对 M4 工具契约设计的硬约束，必须写进工具 Schema（用整数或字符串代替）。
- 不做空值折叠意味着调用方需保证参数构造稳定（例如不要有时传 `{"limit":null}` 有时传 `{}`）。M4 的工具参数构造需从 Schema 默认值统一填充。
- 实现的是 JCS 的**子集**，不是完整 RFC 8785。若未来需要与外部系统交换规范化 JSON，需要重新评估。**这一点必须在文档中如实标注，不能声称"实现了 RFC 8785"。**

## 验证方式

1. 单元测试：键顺序无关性、Unicode 非转义、控制字符转义、整数边界（±(2^53−1) 通过，±2^53 拒绝）、浮点拒绝、深度超限拒绝、重复键拒绝、代理项失配拒绝、`{"a":null}` ≠ `{}`。
2. 属性测试（randomized）：对随机生成的合法参数对象，打乱键顺序后重新序列化，摘要必须不变。
3. 跨语言测试向量：`contracts/tools/digest-test-vectors.json`，Java 与 Python 两侧都必须通过同一份向量（M4 落地 Python 侧时启用）。
4. 集成测试：审批后篡改参数 → 执行被拒 + 审计事件；已消费的审批再次使用 → 被拒。
